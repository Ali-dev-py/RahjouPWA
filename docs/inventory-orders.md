# Outgoing warehouse orders

- Non-visitor inventory access gate applies to listing and creation, including POST.
- Header: Jalali document date, warehouse and optional description. **No branch**: the existing `tblOrderStock` schema has no branch column (confirmed by the user).
- Positive quantities support up to 12 integer digits and 8 decimal places. Products are distinct; duplicate pre-factor lines are aggregated by product on import.
- The import selector contains sales pre-factors only when the master `PrefactorStatusCode` is **4** and `GOrderStockID IS NULL`. Detail status codes and status labels do not determine approval. Purchase pre-factors are excluded; legacy NULL IsBuy is treated as a sale. Details use `GPreFactorMasterID`. The same status-and-unlinked-order rule is checked on import and again during posting. Options show the pre-factor number, actual customer name (resolved through GCustomerID) and date. Customer names are batch loaded, with an explicit unknown label for missing records. The picker supports local search by number/customer/date and shows an explicit empty state.
- Per-form session state records the imported master and original quantities. Server-side comparison detects added/removed products and changed quantities. Deviations return a confirmation screen; its expiring signature binds confirmation to the exact form, source, header and quantities. Changing anything requires renewed confirmation. Import replaces current lines. Multiple open forms have separate IDs (last ten retained).
- Stock is `SUM(Varede) - SUM(Sadere)` in `SanadKala`, filtered by product, selected warehouse and financial year 1405. Absent, negative, zero and insufficient stock block positive issues. **Equal stock is allowed**, as confirmed by the user.
- A single `plus` transaction locks `SanadKala`, then `tblOrderStock` with SQL Server `TABLOCKX,HOLDLOCK`, protecting the stock check through posting and serializing numeric document-number allocation even against desktop writers. These conservative table locks may briefly block other warehouse writes. SQL Server lock behavior requires deployment validation.
- Create master (`OrderKindCode=1`, initial final status 1 and corresponding GUID, creator, Jalali audit dates, warehouse/company/warehouse tafzil), children (quantity, warehouse, product, row number, quality 1), and ledger rows (`OperKind=134`, today's Jalali OperDate, Varede=0, Sadere=quantity, FY1405). `GPreFactorID` stores the imported master's GUID. `GOperID` links each ledger row to the order GUID; OperNo stores order number. Required financial fields default to zero; IsAward/IsOffline/CreateBySaleFactor are false.
- All identity keys, including `SanadKalaID`, are generated by the database, not MAX+1. Document numbers alone are numeric MAX+1 per financial year, capped at 10 digits. All document/line/ledger GUIDs are new UUIDs.
- Creation and read-only listing only: no edit/delete path that could desynchronize posted stock.

Tests use isolated SQLite tables, including rollback, stock boundaries, decimal quantities, approval, import and signed deviation confirmation. SQL Server identities/triggers, concurrency against the desktop application and browser/mobile behavior must still be verified in staging. No schema migrations are needed for these existing unmanaged tables.
